# Tether V1 Guarantee Card

> **Status:** accepted by the owner on 2026-11-12 (direction record TDR-015; U-004 closed in plan step W2.1). The W2.1 review narrowed G-9, G-12, G-13, G-14 and G-16 to what the tests prove and recorded P-16 and P-17 as implemented-but-unproven evidence gaps; the review's evidence map is `docs/testing/strategy.md` §4.
> **Evidence baseline:** commit `ec352540a8fd9f70309b12af53f013b87c2258e4` (`hardening/v1-baseline`, CI green 2026-11-09). Every implementation and test reference below was verified against that commit by reading the code and the test assertions, not the test names.
> **Rule:** §1 contains only statements the baseline implementation proves with automated tests. Anything else is in §2 (planned) or §3 (limits). A guarantee moves from §2 to §1 only with the code, the tests and an owner review.

**Reading an entry.** *Statement* is the guarantee. *Assumptions and exclusions* are the conditions under which it holds. *Implementation* names the code. *Automated evidence* names unit and integration tests and what they assert. *Chaos and race evidence* names the `tests/chaos/` cases. *CI* names the jobs of `.github/workflows/ci.yml` that run that evidence on every push and pull request: `static` (Ubuntu and Windows: `lint`, `typecheck`, `contracts`, `test-unit`), `integration` (Ubuntu: `test-integration`, `test-contract`) and `chaos` (Ubuntu: `test-chaos`). *Failure boundary* says what happens at the edge of the guarantee. *Remaining gap* names evidence that is still missing. Test names are the functions in `tests/`; `poe` tasks are defined in `pyproject.toml`.

**Standing assumption for every §1 entry (OD-4).** Committed authoritative history is never rolled backward. A restore that loses committed Tether state is a recovery discontinuity (§3, `docs/operations/postgres-recovery.md`).

## 1. Guarantees proven at the baseline

### G-1 No external side effect without committed authorization and dispatch records

- **Statement.** A tool is never executed unless a ledger entry for that exact call was created by the run driver under current policy (TX5) and the entry was moved to `dispatched`, with its audit event, in a transaction that committed before the external call (TX6).
- **Assumptions and exclusions.** Applies to tools executed through Tether's worker; graph nodes never perform side effects. Every adoption of persisted state on replay (the decision event, the approval row, the ledger row, and the rows the wait nodes re-read) is hash-checked against the current call under the run's binding key; a diverged LangGraph replay is a `REPLAY_DIVERGENCE` that fails closed (W2.2, below), and the worker executes only the arguments whose hash equals the ledger's.
- **Implementation.** `src/tether/runtime/graph.py` `_authorize` (TX5: current policy asserted and re-evaluated, ledger row and `EXECUTION_AUTHORIZED` in one transaction, `execute_tool` job enqueued with the validated arguments); `src/tether/worker/handlers/execute_tool.py` `_prepare` (TX6: ledger row locked, call hash of the job payload compared to the ledger's, `pending → dispatched` and `DISPATCHED` committed before `_send` runs).
- **Automated evidence.** `tests/integration/test_run_graph.py`: `test_an_allowed_call_is_authorized_into_the_ledger_and_waits_for_the_tool` (ledger row `pending`, job present, `POLICY_DECISION` and `EXECUTION_AUTHORIZED` present before any send), `test_a_denied_call_never_reaches_the_ledger`, `test_invalid_proposals_are_recorded_and_not_executed`, `test_a_tampered_job_payload_is_never_dispatched` (hash mismatch → `failed`, attempts 0, no `DISPATCHED`), `test_an_allowed_read_executes_and_the_run_completes` (event order `DISPATCHED` before `TOOL_OUTCOME`). `tests/integration/test_lock_order.py` (TX7 lock order). Replay integrity (W2.2): `tests/integration/test_replay_divergence.py` (a persisted decision, approval row or ledger row for a different hash is never adopted, overwritten or replaced, nothing is authorized or sent, `REPLAY_DIVERGENCE` is audited; matching hashes adopt as before, including after node-end crashes; a divergence found with a write in flight or `indeterminate` holds the run until the outcome or reconciliation; a stop decides the terminal status with the divergence named in the summary, otherwise `failed` with reason `replay_divergence`; a pending entry is not dispatched once the run has diverged).
- **Chaos and race evidence.** `tests/chaos/test_chaos_crashes.py::test_c01_c04_a_crash_after_each_commit_resumes_without_duplicates` (a crash right after `DISPATCHED` commits, before the send, re-sends with the same key and the target applies once); `tests/chaos/test_chaos_races.py::test_s5_1_cancel_vs_authorization_race_repeated_50_times` (no decision or authorization after a committed stop; a restart happened only when the ledger says `completed`); `tests/chaos/test_chaos_crashes.py::test_a_diverged_replay_after_a_crash_fails_closed_without_sending` (a crash after TX5 or TX3 followed by a row for another call: nothing sent, nothing replaced, `failed`).
- **CI.** `integration`, `chaos`.
- **ADRs.** ADR-0003, ADR-0005, ADR-0007, ADR-0009, ADR-0015; architecture invariants 1, 2, 22.
- **Failure boundary.** A failed audit append or a stop observed in TX5 or TX6 aborts the transaction; the call is `not_applied` and nothing left Tether.
- **Remaining gap.** No test exercises TX5's negative re-checks (policy tightened to deny, changed call, lapsed approval) or a stale policy version at TX5; see G-12 and P-16.

### G-2 A non-idempotent write is sent at most once

- **Statement.** Once a non-idempotent write has been dispatched, Tether never automatically re-sends it. Any unknown outcome becomes `indeterminate`.
- **Assumptions and exclusions.** "Non-idempotent" is the tool author's declaration (`idempotency="unsupported"` on the descriptor; writes must declare it). Tether invokes the handler at most once per logical execution; what the handler does inside one invocation is the tool's responsibility.
- **Implementation.** `execute_tool.py`: `_prepare` refuses a re-send of a `dispatched` entry unless `_resendable` (idempotent) and records `indeterminate`; `_send` retries an unknown outcome only when `_resendable`; `dead_letter` never sends. `src/tether/sdk/tools.py` requires the declaration for writes.
- **Automated evidence.** `tests/integration/test_retries_dead_letter.py::test_t17_an_unknown_non_idempotent_write_is_never_retried` (one send, one effect, `indeterminate`, no `REDISPATCHED`, job done); `tests/integration/test_reconciliation.py::test_t17_a_redelivered_non_idempotent_write_is_not_re_sent` (redelivery after a crash between TX6 and TX7 sends nothing); `tests/integration/test_cancellation_deadlines.py::test_t26_a_cancel_before_dispatch_means_the_write_is_never_sent`; `tests/unit/test_registry.py::test_write_tools_must_declare_idempotency_support`.
- **Chaos and race evidence.** `tests/chaos/test_chaos_races.py::test_c07_f7b_lease_expiry_on_a_non_idempotent_write_is_indeterminate_never_resent` (a second worker takes the job while the first send is still in flight: one send, one effect, the late result cannot overwrite the record); `tests/chaos/test_chaos_crashes.py::test_c07_a_crash_with_a_non_idempotent_write_in_flight_is_held_then_reconciled`.
- **CI.** `integration`, `chaos`.
- **ADRs.** ADR-0007, ADR-0008; architecture invariant 4.
- **Failure boundary.** Worker death, lease expiry or a dropped connection after dispatch → `indeterminate` → the run waits for reconciliation.
- **Remaining gap.** None.

### G-3 Idempotent writes are re-sent only with the same key, within a bound, and never after a stop

- **Statement.** Retries and redeliveries of one logical execution present the same deterministic idempotency key, share one attempt counter bounded by the descriptor, and each re-send is preceded by a committed gate that observed the stop predicate false.
- **Assumptions and exclusions.** The target honours the forwarded key and retains it for longer than recovery takes; the test targets and the demo target do. Two sends with the same key can be in flight at once (lease expiry during a slow send); applying once is then the target's deduplication, not Tether's.
- **Implementation.** `src/tether/core/hashing.py` (`idempotency_key` from run, ordinal and call hash); `graph.py` `_authorize` (key stored on the ledger row at TX5); `execute_tool.py` `_prepare` (TX6r: `REDISPATCHED` committed before the send, refused when the run is stopped or `attempts >= max_attempts`) and `_send` (retry only while `attempt < max_attempts`); `src/tether/queue/backoff.py` (PD-13 delay as the job's `run_after`).
- **Automated evidence.** `tests/unit/test_hashing.py` (key formula, determinism, distinct executions get distinct keys, known-answer vectors); `tests/unit/test_tool_retry_budget.py` (default budget 3, backoff ceilings and jitter); `tests/integration/test_retries_dead_letter.py`: `test_t03_a_retryable_read_failure_is_retried_until_it_succeeds` (same key on every send, one delivery per send), `test_an_idempotent_write_is_retried_with_the_same_key_and_applies_once`, `test_t20_an_idempotent_write_unknown_on_every_attempt_becomes_indeterminate`, `test_t20_a_redelivery_after_the_last_allowed_send_does_not_send_again` (budget spans redeliveries), `test_a_retry_is_not_delivered_before_its_backoff_delay`, `test_a_stop_before_a_retry_means_no_re_send`; `tests/integration/test_cancellation_deadlines.py::test_t26_an_idempotent_write_is_not_re_sent_after_a_cancel`.
- **Chaos and race evidence.** `tests/chaos/test_chaos_crashes.py::test_c05_c06_a_crash_with_an_idempotent_write_in_flight_applies_it_once` (crash before and after the target applied, five repeats each), `::test_a_send_budget_spent_by_crashes_is_indeterminate_then_reconciled`; `tests/chaos/test_chaos_races.py::test_c07_overlapping_same_key_sends_apply_once` (ten repeats).
- **CI.** `static` (unit), `integration`, `chaos`.
- **ADRs.** ADR-0008; architecture invariants 6, 35.
- **Failure boundary.** Budget exhausted with an unknown outcome → `indeterminate`; stop observed before a re-send → no send, `indeterminate` in the same transaction.
- **Remaining gap.** None.

### G-4 Unknown outcomes are never reported as failure; at the baseline only a human resolves them

- **Statement.** A side-effecting result is `not_applied` only with positive evidence; everything else after dispatch is `unknown` and becomes `indeterminate`. The model is never told such a write failed. The entry is resolved only by an eligible reconciler (role, policy eligibility, not the requester) with a justification, recorded as a critical audit event before the run resumes or terminates.
- **Assumptions and exclusions.** "Positive evidence" after dispatch is the tool raising `ToolNotApplied`; Tether trusts that declaration. A write whose pinned tool version is no longer resolvable, or whose job payload no longer matches the ledger's hash, *after* it was dispatched, is left `dispatched` with no outcome and no wake (ADR-0011 version-gone-after-dispatch, plan W5.2); it is not misreported, but it is not resolved either.
- **Implementation.** `execute_tool.py` (`_unknown_state`: unknown write → `indeterminate`, unknown read → typed failure; `ToolNotApplied` → `failed` with the reason; since W3.2 every outcome write states its `outcome_class` (ADR-0021 rule 10, migration `0004`): `ToolNotApplied` and refusals before any send are `not_applied`, a send timeout or ambiguous error is `unknown`, and the model sees `not_applied` only for `not_applied`); `src/tether/api/routers/ops.py` `reconcile_entry` (TX8: role `reconciler`, policy eligibility, reconciler ≠ requester, justification required, conditional `indeterminate → completed/failed/abandoned`, `RECONCILED` and the wake in one transaction); `src/tether/policy/engine.py` `evaluate_reconciliation_eligibility`; `graph.py` `await_tool` (interrupts on `indeterminate`; routes `reconciled_applied`, `reconciled_not_applied`, `abandoned`).
- **Automated evidence.** `tests/integration/test_reconciliation.py` (unknown write → `indeterminate`, never retried, no further model call while waiting; `applied` continues without re-running the tool and the model sees `applied` with the resolution; `not_applied` is definite and a re-proposal gets a new key; `abandon` terminates with no model call; the rest of a turn continues after `applied` and is skipped after `not_applied`; repeat is a no-op, a different outcome is `409`; requester, missing role and other workspace get `404` and change nothing; unknown or resolved entries refused; justification and a known outcome required; stale policy → `503`; dev shortcut refused in prod); `tests/unit/test_reconciliation_eligibility.py` (deny by default, role required, requester never eligible, settings in the policy version); `tests/integration/test_authentication.py::test_t25_a_reconciler_needs_the_ops_audience_the_role_and_not_to_be_the_requester`; `tests/integration/test_run_graph.py::test_a_tool_that_did_not_apply_is_recorded_as_failed`; W3.2 (`tests/integration/test_tool_contract_runtime.py`): a stale target-enforced precondition is `not_applied` with the target unchanged (T-21), an error or timeout while the target checks is `unknown` and an idempotent write then ends `indeterminate`, never `not_applied`; a non-idempotent write that times out is `indeterminate` after one send; a read whose output violates its schema is classified `failed`, an exhausted read `unknown`; the classification CHECK and unclassified historical rows.
- **Chaos and race evidence.** `tests/chaos/test_chaos_crashes.py::test_a_send_budget_spent_by_crashes_is_indeterminate_then_reconciled`, `::test_c07_a_crash_with_a_non_idempotent_write_in_flight_is_held_then_reconciled`; `tests/chaos/test_chaos_races.py::test_a_stop_while_a_write_is_in_flight_never_recalls_it_and_takes_no_new_action` (the `drop` cases); `tests/chaos/test_chaos_tool_contract.py::test_t21_a_stale_precondition_stays_not_applied_across_a_crash` (W3.2: one send, no change at the target).
- **CI.** `static` (unit), `integration`, `chaos`.
- **ADRs.** ADR-0007 (baseline behaviour; superseded by ADR-0019, whose automatic verification is planned P-4 and not current behaviour), ADR-0013, ADR-0018; architecture invariant 5.
- **Failure boundary.** No eligible reconciler → the run waits without holding compute.
- **Remaining gap.** None for the stated behaviour. The "never reported as failure" part is unchanged by ADR-0019.

### G-5 After a stop, no model call starts and no proposal is governed

- **Statement.** Once cancellation is requested or the stored deadline has passed, Tether starts no further model call and governs no further proposal. A stopped run whose write is still unresolved waits, and reconciliation then only records the outcome and terminates the run.
- **Assumptions and exclusions.** A model request that started before the stop committed is not a "further" call (ADR-0006 linearisation point); its proposals are recorded and discarded. Decisions adopted on replay are not new proposals.
- **Implementation.** `graph.py` (`call_model` checks the stop predicate before every provider attempt and again as soon as the response returns; `govern_call`, `request_approval` and `_authorize` refuse when stopped; `stopped()` ends the run `cancelled` or `timed_out` with a summary naming every reconciled outcome); `execute_tool.py` `_prepare` (no first send or re-send once stopped); `src/tether/runtime/stop_requests.py` and `src/tether/worker/handlers/timers.py` (TX9 and TX10 record the request, close pending approvals, audit and wake; they never write the status); `src/tether/storage/repos/runs.py` `_with_stop` (predicate by `clock_timestamp()`; whichever stop came first decides the status).
- **Automated evidence.** `tests/integration/test_cancellation_deadlines.py`: `test_t26_a_run_cancelled_before_it_starts_makes_no_model_call`, `test_t26_a_stop_during_a_model_call_ends_the_run_before_any_proposal` (no decision, no ledger entry), `test_t26_a_final_answer_received_after_a_stop_does_not_end_the_run_as_succeeded`, `test_t26_a_stop_while_awaiting_approval_closes_it_and_a_later_approve_is_refused`, `test_t26_a_cancel_before_dispatch_means_the_write_is_never_sent`, `test_t26_an_unknown_write_after_a_stop_goes_to_reconciliation_then_terminates` (summary names the reconciled outcome; no further model call), `test_t26_cancel_is_requester_only_workspace_scoped_and_idempotent`, `test_the_deadline_timer_records_the_deadline_once`.
- **Chaos and race evidence.** `tests/chaos/test_chaos_races.py::test_s5_1_approve_vs_cancel_race_repeated_50_times`, `::test_s5_1_cancel_vs_authorization_race_repeated_50_times` (no `POLICY_DECISION` or `EXECUTION_AUTHORIZED` after `CANCEL_REQUESTED` in any of the fifty orders), `::test_a_stop_while_a_write_is_in_flight_never_recalls_it_and_takes_no_new_action` (one model call only).
- **CI.** `integration`, `chaos`.
- **ADRs.** ADR-0006, ADR-0008; architecture invariants 9, 16, 28, 29, 35.
- **Failure boundary.** Status becomes `cancelled`/`timed_out` only when the driver next runs; until then clients read the stop flags alongside the status.
- **Remaining gap.** None.

### G-6 Dispatched writes are never recalled, and unknown outcomes are never hidden by a clean terminal status

- **Statement.** Cancellation or deadline never interrupts or recalls a dispatched write. A run is never shown as cleanly `cancelled` or `timed_out` while an outcome is unknown; the terminal summary names any reconciled outcome.
- **Assumptions and exclusions.** The run's agent stays configured in the worker's bootstrap for the life of the run. If an agent is removed from bootstrap and the worker restarts while one of its runs has a dispatched or `indeterminate` entry, `src/tether/runtime/driver.py` `_fail` marks the run `failed` ("agent is not configured") regardless of the ledger. That path never produces `cancelled` or `timed_out`, so the statement holds, but a `failed` status would then stand over an unknown outcome. No test covers it (see §3).
- **Implementation.** `graph.py` (`await_tool` is never short-circuited by the stop flag; `stopped()` is reached only before dispatch or after the entry is terminal; `finalize` writes the summary); `src/tether/worker/handlers/advance_run.py` (`start` holds an `awaiting_reconciliation` run while an entry is unresolved; TX12 moves a run with an unresolved entry to `awaiting_reconciliation`, not `failed`).
- **Automated evidence.** `tests/integration/test_cancellation_deadlines.py::test_t26_a_dispatched_write_is_not_recalled_and_its_outcome_ends_the_run` (the run shows `awaiting_tool` with the flag while the write is in flight; one send; the outcome ends the run), `::test_t26_an_unknown_write_after_a_stop_goes_to_reconciliation_then_terminates` (`awaiting_reconciliation`, then `cancelled`/`timed_out` with `…; probe_nonidem reconciled_<outcome>`); `tests/integration/test_retries_dead_letter.py::test_tx12_advance_run_with_a_write_in_flight_holds_the_run_until_it_resolves`, `::test_tx12_with_an_indeterminate_entry_holds_the_run_for_reconciliation`; W3.2 `fail_run` (T-04, `tests/integration/test_tool_contract_runtime.py`): a read configured to fail the run is held in `awaiting_reconciliation` while another entry is unresolved and fails only once it resolves; an active stop still ends it `cancelled`/`timed_out` with `tool_exhausted:<tool>` in the summary; a reconciled outcome is named in the `failed` summary.
- **Chaos and race evidence.** `tests/chaos/test_chaos_races.py::test_a_stop_while_a_write_is_in_flight_never_recalls_it_and_takes_no_new_action` (cancel and deadline, answered and dropped, ten repeats each); `tests/chaos/harness.py::assert_reconstructable` (a terminal run has no `pending` or `dispatched` entry), run after every chaos scenario; `tests/chaos/test_chaos_tool_contract.py::test_t04_fail_run_survives_a_crash_after_each_commit` (W3.2: six commit points; the run fails once, with no skip events and no further model call).
- **CI.** `integration`, `chaos`.
- **ADRs.** ADR-0006, ADR-0007, ADR-0018; architecture invariants 9, 22.
- **Failure boundary.** A dispatched write with an unknown outcome after a stop becomes `indeterminate`; the run waits in `awaiting_reconciliation` and ends only through TX8.
- **Remaining gap.** The agent-removed-mid-run path has no test and no ADR disposition; recorded for the owner in §3.

### G-7 Terminal run statuses never change

- **Statement.** Once a run is `succeeded`, `failed`, `cancelled`, `timed_out` or `abandoned`, its status cannot change, enforced by a database trigger independent of application code.
- **Assumptions and exclusions.** The trigger guards `UPDATE OF status`. The application role has no `DELETE` on `runs` and cannot disable the trigger; the migrator role and the superuser can alter the schema, as for any database.
- **Implementation.** `src/tether/storage/migrations/versions/rev_0002_core_schema.py` (`runs_status_terminal_guard` function and trigger; grants). Application code also refuses: `RunsRepository.claim_driver_generation`, `fence` and `transition` match only non-terminal statuses; stop requests and timers are no-ops on terminal runs.
- **Automated evidence.** `tests/integration/test_schema.py`: `test_terminal_status_never_changes` (every terminal status, every other target → `check_violation`), `test_the_guard_applies_to_the_owning_role_too`, `test_terminal_runs_still_accept_other_column_updates`, `test_non_terminal_transitions_are_allowed`; `tests/integration/test_permissions.py::test_app_role_cannot_disable_the_terminal_status_guard`, `::test_app_role_cannot_delete_records`; `tests/integration/test_slice_run_lifecycle.py::test_a_terminal_run_is_not_restarted_by_a_redelivered_job`; `tests/integration/test_cancellation_deadlines.py::test_t26_cancel_is_requester_only_workspace_scoped_and_idempotent` (cancel on a terminal run changes nothing).
- **Chaos and race evidence.** `tests/chaos/harness.py::assert_terminal_stable` (a terminal run survives injected wake and deadline jobs, a cancel request and a direct status `UPDATE` as the app role), run at the end of every chaos scenario.
- **CI.** `integration`, `chaos`.
- **ADRs.** ADR-0006; architecture invariant 8.
- **Failure boundary.** Other columns remain writable by design (a stop request on a terminal run is a no-op).
- **Remaining gap.** None.

### G-8 At most one run driver changes a run's authoritative state at a time

- **Statement.** Run driving is serialised by a session-level advisory lock and a per-run fencing token; a driver that lost its lock cannot write, and a contended job is requeued without consuming an attempt.
- **Assumptions and exclusions.** "Authoritative state" is the Tether schema. The LangGraph checkpoint is not fenced: a lock lost after a node's last fenced check but before its checkpoint write can leave a stale checkpoint (ADR-0005 rule 6); this costs liveness, not safety: any resulting fork is caught by hash-checked create-or-get and fails closed with `REPLAY_DIVERGENCE` (W2.2; evidence under G-1).
- **Implementation.** `advance_run.py` (`run_lock` on a dedicated autocommit connection; `start` claims the next `driver_generation`; `Outcome.CONTENDED` → `queue.release` with the attempt refunded); `src/tether/storage/repos/runs.py` (`guard` share-locks the run row and raises `FencedError` on a stale token; `transition` is conditional on the token); `graph.py` (every write node calls `guard` first, in the same transaction as its writes).
- **Automated evidence.** `tests/integration/test_slice_run_lifecycle.py`: `test_two_workers_racing_lease_the_job_once`, `test_contended_run_lock_requeues_the_job_without_consuming_an_attempt`, `test_a_stale_fencing_token_cannot_complete_the_run`, `test_an_expired_lease_is_reclaimed_after_a_worker_crash` (a stale lease token cannot complete the job); `tests/integration/test_retries_dead_letter.py::test_advance_run_delivery_stops_at_max_attempts_and_tx12_fails_the_run` (TX12 takes a fresh token).
- **Chaos and race evidence.** `tests/chaos/test_chaos_races.py::test_three_workers_racing_for_one_run_repeated_50_times`, `::test_c07_four_workers_draining_fifty_runs_never_duplicate_work` (one send and two model calls per run, no leased or dead jobs left), `::test_a_driver_that_lost_its_lock_is_fenced_and_writes_nothing` (its lock connection is terminated, a healthy worker finishes the run, the zombie resumes and appends no event and no model call; ten repeats).
- **CI.** `integration`, `chaos`.
- **ADRs.** ADR-0004, ADR-0005; architecture invariants 10, 30.
- **Failure boundary.** A fenced invocation stops writing; its job is released and re-checks the run.
- **Remaining gap.** None.

### G-9 A crash after any critical commit, during a model call or with a write in flight loses no run and duplicates no idempotent write

- **Statement.** A crash of the API or a worker immediately after any critical transaction commits (TX1 to TX7 and TX11), during a model call, or while an idempotent write is in flight leaves a run that resumes to the same outcome, with no duplicate ledger rows and a target-side write count of one for idempotent writes against a key-honouring target. Hard-killing and restarting the real `api` and `worker` processes mid-run, repeatedly, has the same result.
- **Assumptions and exclusions.** "Supported writes" are writes declared idempotent whose target honours the key; a non-idempotent write in flight during a crash becomes `indeterminate` (G-2). Duplicate ledger rows are prevented by the unique `(run_id, step_ordinal)` constraint. The in-process crash points are a test harness; production processes carry no fault points.
- **Implementation.** ADR-0003 write/wait node discipline (`graph.py`), `durability="sync"` and the three resume modes in `src/tether/runtime/driver.py` (`start`, `resume`, `recover`), create-or-get audit events (`src/tether/storage/repos/audit.py`), lease expiry and redelivery (`src/tether/queue/postgres.py`), the TX catalogue.
- **Automated evidence.** `tests/contract/langgraph/test_durability_sync.py` (a node sees the previous step's checkpoint committed; the `exit` control fails), `test_crash_resume.py` (after `os._exit` mid-node, `invoke(None)` re-runs only that node), `test_interrupt_resume.py` (resume re-executes the wait node; the sentinel is accepted; a spurious wake pauses again); `tests/integration/test_schema.py::test_unique_constraints` (ledger `step_ordinal`); `tests/integration/test_run_graph.py::test_a_redelivered_dispatched_idempotent_call_is_re_dispatched`.
- **Chaos and race evidence.** `tests/chaos/test_chaos_crashes.py::test_c01_c04_a_crash_after_each_commit_resumes_without_duplicates` (twelve commit points, each: `succeeded`, one restart, two completed entries, three model calls, reconstructable, terminal-stable), `::test_c02_a_crash_during_a_model_call_re_calls_the_turn` (three turns; the interrupted attempt leaves no row), `::test_c05_c06_a_crash_with_an_idempotent_write_in_flight_applies_it_once`; `tests/chaos/test_chaos_processes.py::test_c01_c03_hard_killing_the_api_and_worker_mid_run_loses_and_duplicates_nothing` (three cycles of three runs; nine restarts for nine runs; no dead job).

### G-10 Job exhaustion always produces a domain outcome

- **Statement.** A job leased past its maximum attempts is marked dead in the same transaction as a kind-specific transition: `execute_tool` → `failed` (not applied) before dispatch, `indeterminate` for a dispatched write, typed failure for a read; `advance_run` → `awaiting_reconciliation` if an entry is unresolved, else `failed` with `system_error`; always with a wake.

### G-12 An approval is bound to exactly the call it was given and decided only by an eligible approver

- **Statement.** An approval is bound to an HMAC-SHA-256 call hash over the canonical (RFC 8785) envelope of the validated arguments, recorded by the policy decision that required it. Only an approver holding the core `approver` role and a role named by the matching policy rule, who is not the requester, can decide it, once, while it is unexpired; a decision on a lapsed, closed or already decided approval is refused. A write requiring approval executes only after an approval was recorded `approved`, and the worker dispatches only arguments whose hash equals the ledger's. The TX5 re-check before dispatch (a policy that now denies, a changed call, an approval lapsed between decision and execution) is implemented but not yet proven (P-16) and is not part of this guarantee.
- **Assumptions and exclusions.** Since W3.2 (ADR-0021), a write tool's declared preconditions (names and expected values) are part of the envelope and of the approval, and the target enforces them; tools that declare none keep the empty field. The call is bound to its pinned tool version; descriptor metadata (risk, permissions, timeout) is bound through that version, not hashed separately. Approval expiry is one global setting (per-tool expiry is P-8).
- **Implementation.** `src/tether/core/hashing.py` (`CallEnvelope`, `call_hash`, `call_hashes_equal` in constant time); `graph.py` `govern_call` (hash recorded with the decision), `request_approval` (approval row carries the decided hash and masked arguments), `_authorize` (TX5 re-check, untested branches named above); `src/tether/api/routers/approvals.py` (TX4: role, policy eligibility, ≠ requester, `pending` and live, run not stopped or terminal, conditional decide, `APPROVAL_DECIDED`, wake); `src/tether/storage/repos/approvals.py` `decide` (only while `clock_timestamp() < expires_at`); `src/tether/policy/engine.py` `evaluate_approval_eligibility`; `execute_tool.py` `_prepare` (TX6 payload hash check).
- **Automated evidence.** `tests/unit/test_hashing.py` (`test_t08_any_bound_change_changes_the_hash`, call ID and rationale cannot enter the envelope, different binding keys give different hashes, known-answer vectors, constant-time compare); `tests/unit/test_canonical.py` (RFC 8785 vectors, float and integer guards); `tests/integration/test_run_graph.py`: `test_a_call_requiring_approval_pauses_the_run_with_a_bound_request` (approval `call_hash` equals the decision's), `test_an_eligible_approval_executes_the_write_and_completes_the_run`, `test_ineligible_approvers_get_not_found_and_change_nothing` (requester, no role, other workspace), `test_a_rejected_call_is_never_executed`, `test_an_approval_is_decided_once_and_only_before_it_expires`, `test_a_tampered_job_payload_is_never_dispatched`; `tests/integration/test_cancellation_deadlines.py::test_t15_an_expired_approval_is_expired_once_and_the_run_moves_on`, `::test_t15_an_approval_past_its_expiry_is_refused_before_the_timer_runs`; `tests/integration/test_authentication.py::test_t19_an_approver_needs_the_approvals_audience_the_role_and_not_to_be_the_requester` (roles in the body ignored); W3.2: `tests/unit/test_call_hash_preconditions.py` (declared preconditions enter the hash; a changed expected value changes it; no preconditions → unchanged hash), `tests/integration/test_tool_contract_runtime.py` (the approval binds the exact expected values and the approved hash executes with the real values; a re-proposal after `not_applied` gets a new ordinal, key and approval; a retained pinned version executes, evaluated with its own descriptor; a pinned version gone before the ledger is `not_applied` with no newer version substituted).

### G-13 Critical audit events are written inside the state-changing transaction and chained per run

- **Statement.** Every policy decision (including an invalid proposal), skipped call (`CALL_SKIPPED`), approval request, approval decision, dispatch and re-dispatch, tool outcome, reconciliation, stop request, approval closure or expiry, replay divergence, dead-letter and terminal status change is appended in the same transaction as the state it describes; if the append fails, the state change does not happen. Events form a per-run HMAC-SHA-256 chain keyed outside the database, and in-place modification of an event is detected.
- **Assumptions and exclusions.** The chain is per run; cross-run order and deletion are not covered. Each event records how its own MAC is computed (`mac_version`), and one run may mix versions: every event written since W2.4 is version 2, whose MAC covers the stored `created_at`; events written before W2.4 are version 1, remain valid as written and were never re-MACed, and **their timestamps are not cryptographically covered** (W2.4 did not protect them retroactively). Verifying v2 events requires an application that understands `mac_version`; downgrading below migration `0003` after v2 events exist is unsupported, and `0003` must not be rolled out alongside older writers (`docs/operations/production-configuration.md` §6). Tail truncation and whole-run deletion are not detected (ADR-0015 rule 8, design limit); `tether audit verify` additionally compares the persisted head and so exposes deleting events while leaving the head alone, but not deleting them and rewriting the head, nor deleting the whole run. The application role can only insert audit events.
- **Implementation.** `src/tether/audit/chain.py` (`mac_record`, `compute_mac`, `verify_run`, `verify_run_report`); `src/tether/cli/audit.py` (`tether audit verify`, P-9); `src/tether/storage/repos/audit.py` `append` (head row locked `FOR UPDATE`, create-or-get by dedupe key, MAC under the run's pinned audit key, inside the caller's `UnitOfWork`); every TX function in `graph.py`, `execute_tool.py`, `advance_run.py`, `timers.py`, `stop_requests.py`, `tasks.py`, `approvals.py`, `ops.py`; `rev_0002` grants (`audit_events` insert-only for the app role); `src/tether/api/routers/tasks.py` `get_run` (chain verified on inspection).
- **Automated evidence.** `tests/integration/test_audit_chain.py`: `test_events_form_a_verifiable_chain`, `test_a_repeated_dedupe_key_returns_the_persisted_event`, `test_tampering_is_detected` (payload changed by the superuser → chain invalid), `test_concurrent_appends_get_distinct_sequence_numbers`, `test_an_event_rolls_back_with_its_transaction`; a change of one microsecond, one hour or one day to a v2 `created_at` fails verification; a legacy v1 chain written with the old algorithm still verifies, and a payload change on it still fails; a v1 chain continues with v2 events linked to the real v1 MAC, same head and key, and verifies; an unknown version, a v2 → 1 downgrade and a v1 → 2 upgrade each fail; replay adopts a v1 event unchanged; a rolled-back append leaves no event and no head change; migration `0003` marks existing rows v1 without rewriting them, and a write without a version is refused); `tests/integration/test_skipped_calls.py` (W2.3: one `CALL_SKIPPED` per remaining call after a call that did not apply, with the trigger's ordinal, call ID and outcome and no arguments; no decision, approval, ledger row or send for a skipped call; - **Failure boundary.** An append failure raises inside the transaction and rolls back the state change with it.

### G-15 Decisions are made only under the workspace's active policy version

- **Statement.** A policy decision or eligibility answer is recorded only if the evaluating process's loaded policy version equals the workspace's active version read in the same transaction; otherwise no decision is recorded, the job is requeued without consuming an attempt (worker) or the API returns `503` with no state change.

### G-16 Every request-path query after authentication is workspace-scoped

## 3. Operating limits and known limitations at the baseline

- **Not measured.** No performance or load suite exists; P-01–P-03 are targets. Development defaults: worker lease 60 s, poll 1 s, run deadline 3600 s, approval TTL 3600 s, model turn bound 8, tool send attempts 3, job attempts 8 (`advance_run`) / 5 (`execute_tool`) / 10 (timers).
- **No lease heartbeat.** A tool call longer than the lease is redelivered (idempotent) or becomes `indeterminate` (non-idempotent) even if healthy. Since W3.2 each send is bounded by the tool's `timeout_seconds` (default 10 s, at most 300 s; a timeout is `unknown`), and the worker refuses to start with any offered or retained tool whose timeout is not below the lease (ADR-0021 rule 6).
- **No production model provider.** The scripted provider is the driver's default and refuses only `prod`; no OpenAI adapter exists yet, and provider selection is not configurable.
- **Environment default.** `TETHER_ENV` defaults to `dev` when unset, which enables the dev identity shortcut and the scripted provider. D-12 requires this to fail closed (P-14).
- **Approvals.** Decision endpoint only; no list, detail or approver run view (P-10).
- **Audit.** Timestamps of version-1 events (written before W2.4) are outside their MAC and stay so; version-2 events cover theirs. No audit query; access events not written; waiting-status transitions (`running`, `awaiting_*`) are not audited and no ADR requires it.
- **Replay.** Hash-checked create-or-get with `REPLAY_DIVERGENCE` (W2.2): a divergence writes the audit event, blocks further model calls, authorizations and sends, holds the run while any ledger entry is unresolved, and then ends it. The stop predicate still decides the terminal status (ADR-0006): `cancelled`/`timed_out` with `replay_divergence` named in the summary when a stop is active, otherwise `failed` with reason `replay_divergence`. The evidence is never rewritten or removed.
- **Known failure boundaries found in W2.1 (owner dispositions 2026-11-12):**
  - *Agent or configuration unavailable mid-run (correctness gap, scheduled in W5.2; scope delta I-4).* Today, if a worker starts with a bootstrap that no longer configures a run's agent, `driver.py` `_fail` marks the run `failed` ("agent is not configured") even when a ledger entry is `dispatched` or `indeterminate`, so a `failed` status can stand over an unknown outcome; no test covers the path. Required semantics: Tether must never hide an unresolved real-world side effect by terminally failing a run because its agent or configuration disappeared. (1) With no unresolved consequential side effect, the run may terminate `failed` with a typed configuration-unavailable reason. (2) With an unresolved consequential side effect, including an outcome whose real-world truth still needs resolution, the run must not be terminally failed for that reason. (3) No further model call, new authorization or external send may occur while the required configuration is unavailable. (4) The unresolved state is preserved and the run is held or routed through the reconciliation semantics. (5) Once every unresolved effect is resolved, if the configuration is still unavailable and execution cannot continue, the run may terminate `failed` with the explicit reason. (6) Inspection and audit keep exposing the unresolved or reconciled action and never let the configuration failure read as "the external effect did not occur". Regression coverage is required with the fix.
  - *Tool version or payload no longer valid after dispatch.* A `dispatched` entry whose pinned tool version is unresolvable, or whose job payload hash no longer matches, is left `dispatched` with no outcome, no wake and a completed job; the run waits in `awaiting_tool` indefinitely (ADR-0011 version-gone-after-dispatch; plan W5.2).
  - *Retained evidence gaps* (strategy §4.1): TX5 refusal branches and stale policy at TX5 (P-16); end-to-end `Sensitive` run coverage (P-17); approval route stale-policy `503`; tool version unavailable after dispatch; the 20× chaos flake gate in CI.
- **Single Postgres instance** is the only stateful dependency and a single point of failure: while it is down nothing progresses and nothing is lost. **Every guarantee in §1 assumes committed authoritative history is never rolled backward.** A restore that loses committed Tether state is a recovery discontinuity: external effects in the lost interval cannot be reconstructed from the database, and side-effect dispatch must enter an operator-controlled recovery posture before it resumes (OD-4). Guidance: `docs/operations/postgres-recovery.md`.
- **Scale claim.** "Production-shaped correctness at modest, measured scale." No concrete concurrency, latency or throughput limit is claimed until W10.3 measures it (OD-3).
- **Tail truncation and whole-run deletion** of audit chains are not detected (ADR-0015 rule 8, design limit).
- **Mid-run revocation** of a requester is not guaranteed; exposure is bounded by approval expiry and the run deadline.
- **Hosted-provider egress.** Non-sensitive tool output placed in model context leaves the deployment when a hosted provider is used.
- **Data retention** is undecided; nothing is deleted.
